# Управляемый контекст — дополнение к инженерному плану

Статус: принято в объём работ по запросу пользователя. Наличие этого документа
не означает, что настройки уже реализованы. Расширяет разделы 9, 12 и 13
основного плана; применяется к Agent и Team через одну серверную политику.

Текущий срез реализации (ещё не полный выпуск): добавлены
`ContextPolicy`, расчёт полного входного бюджета, параметры существующего
`compact_working_context`, наследуемое SQLite-хранение и owner-scoped API.
Под флагом `ODYSSEUS_CONTEXT_POLICY_ENABLED=1` вместе с engineering-флагом
сохранённый профиль пользователя применяется в Agent, а наследуемый профиль
задачи/исполнителя — в Team. UI управляет пользовательским, проектным уровнями,
текущей задачей Team и выбранным исполнителем; имеет 11 параметров, RU/EN,
историю и защиту конфликтов. Выбор привязан к текущему snapshot Team, проект
задачи определяет сервер. Переход в другой чат удаляет старую привязку;
обычное обновление snapshot сохраняет черновик того же исполнителя.
Контекст одиночного чата как отдельная область UI, библиотека именованных
пользовательских пресетов, другой суммаризатор, ручной coordinator/checkpoint и полная
приёмка ниже пока не завершены. Production-флаги этим срезом не включались.
Существующие задачи без явно сохранённого профиля не мигрируются на новые значения.
Добавлены три встроенных пресета как черновики: предпросмотр, явное внесение и
отдельное сохранение через существующую политику. Выбор не вызывает модель;
резерв ответа и окно не меняются. RU/EN и сценарий сохранения проверены в Chrome.
Связь Team → форма, отдельное сохранение задач/исполнителей, отсутствие влияния
на соседнего исполнителя и очистка при смене чата проверены двумя Chrome-сценариями
на тестовом HTTP API. Реальное SQLite-наследование и runtime Agent/Team отдельно
проверены на ARM в изолированном контейнере: 37 tests + 2 subtests passed.
Это не сквозная проверка с реальной LLM и не включение production-флагов.
Добавлен перенос профилей JSON v1: экспорт только сохранённых переопределений,
без scope/endpoint/истории; импорт до 32 КиБ со строгими полями и типами,
предпросмотром и отдельными действиями внесения в черновик и сохранения.
Версии 0/неизвестные версии не мигрируются догадками, а явно отклоняются.
Файл не предоставляет полномочий; сохранение проходит существующий серверный API
с CAS и проверкой согласованности политики. Проверены скачанный JSON, ошибочные
профили, RU-сообщения, сохранение только выбранного исполнителя и отсутствие POST
при импорте/экспорте. Именованная серверная библиотека пресетов остаётся открытой.
Для Team UI отдельно показывает политику последнего завершённого модельного
запроса из сохраняемого журнала worker_metrics: точную пару endpoint/model,
версии политики, окно и бюджет, оценку входа и фактически переданный max_tokens.
Изменение политики не переписывает наблюдение: UI показывает несовпадение версий.
Потерянный/ошибочный ответ не создаёт наблюдения завершённого запроса; обычный
запрос без профиля не должен показывать старую политику как последнюю.
Эта панель не описывает ещё выполняющийся запрос и не выдаёт оценку за backend usage.
Наблюдение автоматически перечитывается по worker_metrics в существующем Team SSE,
при открытии панели и восстановлении соединения. Обновляется только блок наблюдения,
не поля/пресеты/импортированный черновик. Одновременные обновления объединяются;
устаревший ответ другой области игнорируется. Изменение серверной версии запрещает
сохранение до явной перезагрузки, сохраняя черновик. Сбой обновления показывает
локализованное предупреждение об устаревших данных, без накопления повторных ошибок.
Без Team-событий видимая страница проверяет текущую политику раз в пять секунд
через существующий owner-scoped API; после возврата в видимую вкладку — сразу.
Это фоновый опрос версий, не новая SSE-подписка. Он охватывает пользователя,
проект, задачу и исполнителя; не заменяет черновик и не запускает модель.
При конфликте блокируется сохранение до явного обновления, а прежняя проверка
валидности отмечается устаревшей. Скрытие страницы, отключение возможности и
уничтожение панели останавливают опрос. Chrome HTTP-fixture проверяет фоновое
обнаружение owner-policy, сохранение черновика, отсутствие POST, обработчик
видимости и очистку таймера. Физическое переключение устройств ещё не проверено.
Тем же циклом журнал изменений политик получает следующую страницу по курсору.
Пустая страница не перестраивает существующие строки; после временной ошибки
история восстанавливается без дублей. Фоновая загрузка не изменяет черновик.

## 1. Уровни и совместимость

Новые снимки Agent содержат SHA-256 endpoint_key без URL/учётных данных.
Источник берётся из фактически сформированного candidate request, включая
fallback. Нормализатор сохраняет только корректный 64-символьный hex-ключ;
API индикатора не использует live/исторический snapshot с ключом другого endpoint
при совпадающем имени модели. Старые snapshots без ключа остаются совместимыми,
но не доказывают endpoint-привязку. API также возвращает current_endpoint_key.
Прямой SSE-клиент сверяет новый ключ с серверной привязкой и текущим выбранным
URL. При неизвестной/изменённой привязке объединяет запросы её обновления и не
отображает неподтверждённое измерение. Поздний HTTP-ответ другого выбранного
endpoint/model также игнорируется. Реальный chat.js проверен в Node VM с
изолированным DOM: совпадение, другой ключ, неверный формат и смена URL при том
же model ID. Совместный ARM-набор: 33 tests + 2 subtests passed,
`/home/xopmc/services/odysseus-qa-endpointsse-fXq4kG`.
Физическое переключение моделей в полном браузерном приложении ещё не проверено.
ARM: 134 tests + 2 subtests passed (runtime usage, Agent policy, foreground routing),
snapshot `/home/xopmc/services/odysseus-qa-endpointcontext-k9EHlW`.

Новый кандидат: серверный `session_id` добавляет отдельный слой обычного чата
после owner. Владелец проверяется по записи sessions в основной БД; чужой или
отсутствующий чат недоступен, смешение session/Team scope отклоняется.
Agent разрешает эту политику на прежних границах формирования запроса и проверки
версий, включая fallback. Прежнее тело API без session_id совместимо.

`/home/xopmc/services/odysseus-qa-chatpolicy-2RjlBy`, включая реальный SQLite

## 2. Настройки в UI

Дополнительная защита: до запроса суммаризатора проверяется размер системных
инструкций, целей и закреплённых полных обменов. Если уже они достигают целевого
бюджета, возвращается uncompactable с исходными сообщениями без вызова модели.
Регрессия сначала воспроизвела лишний запрос, после исправления локальные
11 context-policy tests и 5 dynamic-menu-i18n tests проходят. В RU/EN-панель
добавлено пояснение приоритета минимального числа групп над токеновым бюджетом.
Это проверка логики и наличия переводов; новый текст ещё не проверен визуально.

Проверка runtime сохранения истории: исправлено принудительное удержание первого
необязательного сообщения при recent_groups=0 и недостаточном recent_tokens.
Теперь нулевые значения действительно отключают необязательную дословную историю;
исходная/последняя цель и закреплённые обмены остаются защищёнными. Минимальное
число групп имеет приоритет над токеновым бюджетом; обязательный обмен не режется.
Два новых теста сначала воспроизвели uncompactable, после исправления проходят.
На ARM snapshot `odysseus-qa-retention-kO1Bct` набор context_policy,
agent_working_context, agent_context_policy, team_context_policy прошёл:
44 tests + 8 subtests, exit 0. Это проверка кандидата без production-данных,
не обновление рабочего сервиса и не полная приёмка управления контекстом.

- Два уровня интерфейса: основные настройки и «Расширенные параметры».
  Не перегружать обычный чат всеми полями одновременно.
- Пресеты «Сбалансированный», «Долгая агентская задача», «Бережно к памяти»
  и пользовательские профили. Перед применением показывать конкретные изменения,
  а не скрыто заменять значения. Название пресета не гарантирует качество модели.
- Предпросмотр эффективного бюджета и предупреждений без обращения к модели.
  Кнопки «Применить», «Отменить изменения», «Сбросить к родительскому профилю»;
  сохранение настроек само по себе не запускает платное или локальное сжатие.
- Подсказки с единицами измерения, допустимыми диапазонами и компромиссами каждого
  параметра. Ошибки согласованности показываются у соответствующих полей.
- Точки входа: «Настройки → Контекст» для профиля владельца и кнопка текущего
  контекста в чате для переопределения задачи. В карточке исполнителя — его профиль.
  Нельзя выдавать сохранение глобальных настроек за изменение конкретного чата.
- Привязка ограничения окна к точной паре endpoint/model, а не только имени модели.
  При смене модели пересчитать бюджет, показать несовместимые параметры и источник
  фактического окна; не переносить неподтверждённую ёмкость с другого endpoint.
- Экспорт/импорт пользовательских профилей с версией схемы, без секретов и истории
  чатов. Импорт сначала показывает diff и проходит ту же серверную валидацию.
- Именованная библиотека профилей: создать, сохранить копию, переименовать,
  обновить и удалить через UI. Библиотека принадлежит владельцу; изменения
  версионируются, список имеет поиск и постраничную выдачу.
- При сохранении профиля явно выбирать полный снимок эффективных настроек или
  только переопределения. Предпросмотр применения показывает, какие значения
  наследуются и какие будут заменены, включая окно и резерв ответа. Удаление
  пресета не сбрасывает уже применённые настройки работающих задач.
- Выбор пресета сначала заполняет черновик; применение к выбранной области —
  отдельное действие. Сохранение, просмотр и удаление пресета не вызывают модель.
  Некорректный для новой модели профиль нельзя применить без исправления;
  автоматическое увеличение реального окна backend запрещено.

### Бюджет

- Автосжатие: включено/выключено; ручное сжатие остаётся доступным.
- Запрашиваемое окно контекста и отдельно подтверждённое окно backend.
- Резерв ответа: токены и ограничение фактического max_tokens следующего запроса.
- Запас безопасности оценки: абсолютные токены и процент.
- Порог запуска: процент доступного входного бюджета, с показом числа токенов.
- Целевая заполненность после сжатия (гистерезис), меньшая порога запуска.
- Предел результата одного инструмента, лимит схем инструментов и загрузка
  больших результатов порциями/через артефакты, а не незаметное удаление данных.
- Предупреждение о переполнении и поведение при выключенном автосжатии:
  приостановить запрос и предложить действие; не обрезать требования молча.

Расчёт: доступный вход = подтверждённое окно − резерв ответа − запас.
Вход включает system prompt, сообщения, tool schemas, tool results, изображения
и прочие части запроса с учётом доступности достоверного подсчёта backend.
Процент должен подписываться однозначно: от полного окна или входного бюджета.
Не разрешать UI увеличивать реальную ёмкость модели произвольным числом.

### Сохранение информации

- Число последних полных шагов/раундов, сохраняемых без сжатия.
- Минимальный токеновый бюджет недавней истории.
- Целевой и максимальный размер резюме.
- Стратегия: структурное резюме; сначала перенос больших tool outputs в артефакты;
  комбинированная. Потеря доступности артефакта должна отображаться явно.
- Сохраняемые разделы: цель, требования, ограничения, решения, проверенные факты,
  пути/хеши, результаты проверок, отвергнутые гипотезы, незавершённые действия.
- Пользовательские закреплённые сообщения/факты с оценкой занимаемого бюджета.
- Инструкции безопасности, действующие разрешения и неопределённые побочные
  эффекты не разрешается удалить переключателем сжатия.
- Пара tool_call/tool_result неделима; незавершённый вызов не теряется.

### Выполнение сжатия

- Суммаризатор: текущая модель или выбранная точная пара endpoint/model из
  разрешённого пула. Внешняя модель требует отдельного согласия на данные и бюджет.
- Максимальный ответ суммаризатора, тайм-аут и ограниченное число попыток.
- Минимальный интервал в завершённых шагах между сжатиями и предел последовательных
  неэффективных сжатий. Контроль предельного окна важнее минимального интервала:
  при недостаточном бюджете следующий запрос блокируется, а не переполняется.
- Проверка, что новое резюме меньше исходного и сохраняет обязательные разделы.
- При ошибке сжатия сохранять исходный checkpoint и понятную причину, не отправлять
  заведомо переполненный запрос и не повторять инструменты с побочными эффектами.

## 3. Панель «Контекст»

- Полное окно, фактический вход, резерв ответа, запас, закреплённая и недавняя
  история, system/tools, доля изображений при доступности измерения.
- Источник счётчика: backend / локальный токенизатор / оценка; дата измерения,
  конфигурация endpoint/model, предупреждение о несовпадении с backend.
- Предварительный расчёт эффекта настроек без скрытого модельного запроса.
- Действия: «Сжать сейчас», «Сжать на следующем шаге», «Просмотреть резюме»,
  «История сжатий», «Сбросить переопределения».
- В Team: общий обзор и отдельный контекст каждого исполнителя, без автоматического
  копирования полного родительского чата.
- Журнал: причина, политика/версия, before/after tokens, длительность, модель,
  стоимость/оценка, сохранённые ссылки, ошибка. История и изменения синхронизируются
  между устройствами через сохраняемые события.
- RU/EN для всех подписей, подсказок, ошибок валидации и состояний этой панели.

## 4. Серверная реализация

- Версионированная схема ContextPolicy и единственный расчёт эффективного бюджета.
- Owner-scoped API чтения/изменения с optimistic locking, диапазонами и проверкой
  согласованности параметров. Клиентские значения не являются полномочиями.
- Один compaction coordinator для Agent/Team: блокировка на конкретный контекст,
  checkpoint до изменения, атомарная замена после проверки, событие результата.
- Сериализовать одновременные ручное и автоматическое сжатия; идемпотентный ID.
- Перезапуск не запускает повторно неизвестный модельный запрос или команду.
- Сжатие не даёт внешнему суммаризатору доступ к данным без согласия; секреты не
  добавляются в резюме или журналы по причине изменения политики.

## 5. Приёмка

1. Порог, резерв, целевой размер и сохранение последних раундов реально меняют
   отправляемый запрос; UI-кнопки без runtime-эффекта не считаются реализацией.
2. Замер охватывает весь запрос, а не короткую сохранённую историю чата.
3. Проверены разные окна, недостоверный/отсутствующий usage, большие tools и images.
4. Несогласованные значения отклоняются; резерв не может оставить отрицательный
   входной бюджет; целевой размер сжатия не превышает доступный бюджет.
5. Проверены Agent и несколько исполнителей Team, независимые политики и очередь
   одной модели Jetson без нарушения `--models-max 1`.
6. После нескольких сжатий сохраняются исходные требования, права, артефакты и
   неизвестные результаты операций; нет повторных побочных эффектов.
7. Проверены отказ суммаризатора, timeout, отмена, отзыв разрешений, restart и
   одновременная ручная команда с двух устройств.
8. Платный/внешний суммаризатор без разрешения и бюджета не вызывается.
9. Значения сохраняются после reload/restart, RU/EN корректны на телефоне и desktop.
10. Финальный двухчасовой сценарий использует эти настройки и включает несколько
    реальных сжатий. Старый короткий тест не заменяет эту приёмку.
11. Настройка из чата изменяет именно выбранную задачу; изменение профиля одного
    исполнителя не меняет соседних. Два одноимённых model ID разных endpoints
    сохраняют раздельные подтверждённые окна и расчёты.
12. Проверены RU/EN для каждой настройки, единиц, подсказок, ошибок и источников
    наследования, а также импорт старой/неизвестной версии профиля без тихой потери
    параметров. Экспорт не содержит данных задачи или учётных данных.

## 6. Порядок доведения до выпуска

### Обязательная карта настроек перед выпуском

В интерфейсе настройки сгруппировать, а не показывать одной длинной формой:

| Группа | Управляемые параметры |
|---|---|
| Автосжатие | Включение, порог запуска, целевая заполненность, интервал между сжатиями |
| Бюджет запроса | Запрашиваемое окно, резерв ответа, абсолютный и процентный запас |
| Сохраняемая история | Полные последние раунды, их токеновый бюджет, закрепления, обязательные разделы |
| Резюме | Стратегия, целевой размер, максимальный ответ, выбранный суммаризатор |
| Инструменты | Размер вывода, порционная выдача и перенос в артефакты, бюджет схем |
| Надёжность | Тайм-аут, предел попыток, предел неэффективных сжатий, поведение при нехватке места |

У каждой группы показывать доступность в текущем backend, источник наследования
и состояние применения. Технические ограничения безопасности и реальное окно
backend не являются отключаемыми настройками. Если закреплённые требования,
неделимые вызовы инструментов и резерв уже не помещаются, явно предлагать уменьшить
бюджеты или сменить модель; не удалять защищённый контекст автоматически.

Проверка полноты блока должна перечислять каждое поле из этой карты. Наличие
только переключателя автосжатия и процентного порога не закрывает требование
пользователя о расширенном управлении контекстом.

Обязательный критерий управляемости: константы в коде допустимы как начальные
значения и технические пределы, но не заменяют сохраняемые настройки пользователя.
Для каждого доступного поля вести соответствие «поле UI → серверная политика →
потребитель в runtime → положительный и отрицательный тест». Показывать отдельно
сохранённое значение, эффективное значение с учётом наследования и значение,
применённое к последнему запросу. Если изменение ожидает безопасной границы,
отображать «Применится к следующему запросу», а не создавать впечатление, что
уже отправленный контекст изменился. Все эти состояния также переводятся на русский.

1. Завершить единый расчёт и применение всех параметров в Agent/Team; каждое поле
   UI сопоставить с runtime-эффектом и тестом. Неподдерживаемые поля недоступны
   с объяснением, а не сохраняются как будто они действуют.
2. Подключить контекст конкретного чата и исполнителя, предпросмотр бюджета,
   пресеты, импорт/экспорт и полную локализацию.
3. Добавить долговечное ручное сжатие, закрепления, стратегию артефактов и выбор
   суммаризатора с проверками разрешений, отмены и восстановления.
4. Выполнить приёмку выше на финальном кандидате; только затем включить управление
   на Jetson с сохранением существующих настроек. Частично реализованные параметры
   и проверка только на тестовом сервере не означают готовность всего блока.
